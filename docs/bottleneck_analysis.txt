Bottleneck Analysis — Lab 7: Trace-Based Performance Review
=============================================================

After running 5 complex queries through the agent and analyzing execution
traces, the primary bottleneck is the LLM inference step in the agent_node.

FINDINGS:

1. LATENCY BOTTLENECK: The agent_node (LLM reasoning) accounts for ~88% of
   total execution time. Each ReAct loop iteration requires a full LLM call
   to Gemini (gemini-flash-latest), averaging 1,600-1,900ms per call. A
   typical single-tool query requires 2 agent_node invocations (initial
   reasoning + final answer), while a multi-step workflow requires 3-4
   invocations, pushing total latency to 6-8 seconds.

2. TOOL EXECUTION: All tool functions (get_employee_info, get_task_status,
   check_compliance_status, etc.) execute in under 120ms since they read
   from local SQLite and ChromaDB. The tool_node is NOT a bottleneck.
   The ChromaDB vector search (query_onboarding_policy) is the slowest
   tool at ~120ms, but still negligible compared to LLM latency.

3. GUARDRAIL OVERHEAD: The guardrail_node adds ~350ms when running the
   LLM-as-a-Judge (Approach B). The deterministic check alone takes <5ms.
   For production use, the deterministic-only path could be used for most
   requests, reserving LLM-as-a-Judge for ambiguous inputs.

4. FAILURE POINT IDENTIFIED: In 1 of 5 complex queries, the agent entered
   an extra reasoning loop because the LLM attempted to call a tool with
   slightly incorrect arguments (wrong task name format). The tool returned
   an error, and the agent self-corrected on the next iteration, adding
   ~3,500ms of unnecessary latency. Root cause: the LLM occasionally
   paraphrases task names instead of using exact names from the database.

PROPOSED FIXES:

1. REDUCE LLM CALLS: For common single-tool queries (e.g., employee info
   lookup), consider a "fast path" that bypasses the ReAct loop and
   directly calls the appropriate tool based on intent classification.

2. TOOL RESULT FORMATTING: Return tool results with explicit "use this
   exact name" hints to reduce argument mismatch errors that cause
   unnecessary retry loops.

3. CACHING: Implement a short-lived cache for tool results (e.g., 60-second
   TTL for employee data) so that repeated calls within the same session
   return instantly.

4. GUARDRAIL OPTIMIZATION: Use the deterministic guardrail as the primary
   layer and only invoke the LLM judge when the input is ambiguous (e.g.,
   partial keyword matches). This saves ~350ms per request for clearly
   safe or clearly unsafe inputs.
